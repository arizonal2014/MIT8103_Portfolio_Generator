# Shared case specification

The specification is the proposed design shared by all five portfolios. It is data, not an executable script. It prevents later stages from accidentally using different table names or unrelated scenarios.

## Contents

The [JSON schema](schema/case-spec.schema.json) defines version 1:

| Section | What it stores |
| --- | --- |
| scenario | Title, description, users, operations, scope and assumptions |
| entities | Fields, restricted types, required values, primary keys, unique keys and foreign keys |
| businessRules | Named rules, their entities/fields and proposed enforcement |
| queries | Connected join, filter and aggregate query plans |
| optimisation | Benchmark entity and field, a B-tree index plan and bounded synthetic row count |
| transactions | Proposed commit, rollback and concurrency exercises tied to a declared rule |
| noSql | MongoDB collection, related source/embedded entities and differing event details |
| distributed | A proposed three-member replication discussion, not a running deployment |
| syntheticDataOnly | Must be true |

The 2-8-table range and 10,000-100,000 benchmark-row range are prototype resource limits, not assessment requirements. Types are model-level values; executable SQL types and constraints still need a later renderer. Compound keys are supported by the contract. Cardinalities are derived from foreign keys, nullability and declared uniqueness rather than separately invented for the diagram.

## Checks

[The validator](lib/case-spec.mjs) uses the trusted schema to reject unknown properties, unsupported types and unsafe identifier shapes. Cross-checks reject duplicate table/field/rule/query names, missing fields and referenced tables, optional primary keys, incompatible foreign-key types, non-unique referenced keys, disconnected joins and inconsistent transaction/NoSQL references.

The model fingerprint is a SHA-256 digest of its canonical JSON. Later stages can use it to detect a changed input. No execution cache or automatic invalidation engine is implemented yet.

Structural validity does not establish domain correctness. Check expressions, filtered-uniqueness predicates, seed records, worked normalisation tables, executable transaction schedules and test assertions are not generated by this contract. A separate [SQL renderer and hospital pilot](PostgreSQL_Execution.md) now bind and test a restricted set of explicit rules. Cyclic references are handled by adding foreign keys after all tables; optional compound keys still use PostgreSQL's default MATCH SIMPLE semantics. No speed improvement, isolation behaviour or failover is inferred from this model.

## Local integration

- `validateCaseSpec(object)` returns validity, errors, warnings, derived relationships and a fingerprint when valid. It does not mutate the object or execute its descriptions.
- `parseCaseSpec(text)` rejects malformed/fenced JSON and responses over 100 KB.
- `buildCasePrompt(caseStudy)` creates a provider-neutral prompt and includes the contract. It does not include the separately collected student name or ID. It makes no network request and is not a security boundary for later execution.
- `GET /api/case-spec/schema` returns the contract.
- `GET /api/examples/library` and `/api/examples/hospital` return clearly labelled hand-written examples.
- `POST /api/case-spec/check` validates the submitted `spec` property without saving a run.
- `createScaffold(input, runsDirectory)` can accept an additional `caseSpec`. Invalid models are rejected before folder creation. A valid model adds prefixed `CaseSpec.json` and `CaseValidation.json` files to the new run. All execution stages remain pending.

The browser's developer panel validates examples without attaching one to a student's form or silently replacing their case study. The future provider adapter must generate from that student's actual scenario and supply a validated response to the runner. A structural check alone cannot prove that a model matches free-text scenario requirements.
